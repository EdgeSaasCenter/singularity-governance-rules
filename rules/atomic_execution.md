# Diretiva de Execução Atômica

Esta regra força o agente a abandonar o comportamento acelerado de "atropelar" tarefas, impondo uma contenção cirúrgica focada em extrema granularidade.

1. **Granularidade Interpretativa (Fim do Mecanicismo):** Nunca reduza a arquitetura a passos triviais e mecânicos. As micro-etapas não devem ser ações físicas vazias (Ex: "abrir arquivo", "checar yaml"). Elas devem representar avanços cognitivos e arquiteturais significativos (Ex: "Analisar impacto do Circuit Breaker na latência"). Se uma etapa parecer complexa, ela não é uma etapa: transforme-a em um Módulo inteiro com suas próprias sub-etapas interpretativas. Mais etapas profundas, zero burocracia mecânica.
2. **Ciclo Restrito & Encadeamento Autônomo:** Para cada Micro Etapa, execute o ciclo rigoroso: `Dissertação -> Aplicabilidade -> Teste Real`. Não emende duas micro-etapas no mesmo turno. Porém, se o teste real (Auditoria) confirmar 100% de sucesso e houver próximas etapas aprovadas no Manifesto, você DEVE engatilhar o Turno 1 da PRÓXIMA etapa de forma autônoma usando a ferramenta `schedule` (Timer). Não exija autorização humana para avançar.
3. **Registro Físico OBRIGATÓRIO:** O resultado tangível e os testes da Micro Etapa jamais devem existir apenas como texto no chat do Agente. Eles DEVEM gerar um documento físico de evidência (ex: `micro_etapa_001.md`) que será salvo obrigatoriamente dentro de `docs/micro_etapas/fase_X/` na raiz do projeto do usuário. O agente não pode avançar para o passo N+1 sem comitar a evidência física do passo N.

   **Gate de Encerramento Obrigatório (Anti-Skip de Evidência — Falha Empiricamente Documentada em 2026-08-19):** Antes de encerrar qualquer resposta que contenha: (a) novo código de produção; (b) novo artefato de pesquisa; ou (c) novo resultado de benchmark — o Agente DEVE verificar se o arquivo `docs/micro_etapas/fase_X/micro_etapa_NNN.md` correspondente foi criado **no mesmo turno**. Se não foi, a criação do arquivo de evidência é a **ÚLTIMA ação obrigatória do turno** antes de qualquer texto de resposta ao usuário. É expressamente proibido criar a evidência retroativamente (após o usuário perguntar onde está). A criação retroativa é considerada violação de integridade de processo, não uma correção aceitável.
4. **Dimensionamento Dinâmico (Fim dos Números Mágicos):** Não force um número fixo de etapas ou módulos (ex: "sempre 60"). A quantidade de módulos e sub-etapas deve nascer organicamente da complexidade real da tarefa (podem ser 30, 80, 200). Aplique o fatiamento fractal de forma fluida, adaptando-se estritamente à biologia do problema, sem gerar etapas inúteis apenas para bater uma meta numérica.
5. **Lei do Micro-Planejamento Contínuo (Anti-Execution Bias):** Mesmo operando sob um Manifesto validado, o Agente é ESTRITAMENTE PROIBIDO de agir no "piloto automático". Para qualquer etapa que envolva a criação de lógica de código ou novas ferramentas, a fase de `Dissertação` deve atuar como um **TDD Arquitetural Preventivo**. O Agente deve aplicar a regra de destruição de ideias: critique ativamente a primeira solução óbvia antes de escrever o código físico. Se a etapa se provar de alto impacto sistêmico, o Agente deve pausar a execução atômica, redigir um `implementation_plan.md` (Micro-Plano) exclusivo para aquela etapa e aguardar a validação do usuário antes de codificar.
6. **Lei do Pessimismo Arquitetural (Anti-Strawman e Carga Hostil):** Durante a fase de `Teste Real` (Dry-Run) ou `TDD Arquitetural`, o Agente é EXPRESSAMENTE PROIBIDO de usar exemplos triviais ou apenas o "caminho feliz" para validar suas hipóteses. O teste DEVE obrigatoriamente incluir uma carga hostil/maliciosa para comprovar que o Circuit Breaker explodirá graciosamente, além da carga saudável. O teste mental DEVE sempre invocar o cenário mais complexo, hostil e catastrófico possível dentro dos limites de atuação da feature. O Agente também é proibido de declarar "segurança estrutural absoluta" se o manifesto ainda prever etapas de checagem de dependência cruzada no futuro.
7. **Lei da Visão Sistêmica (Anti-Análise Isolada):** Ao avaliar o impacto de uma modificação arquitetural, o Agente é PROIBIDO de analisar apenas a fase/componente imediatamente adjacente. Ele DEVE mapear o impacto em TODA a cadeia de execução do sistema, do ponto de entrada ao ponto de saída. Uma análise de impacto que ignora downstream (o que acontece depois do ponto modificado) é considerada incompleta e não pode gerar a conclusão de "segurança estrutural". Antes de declarar um impacto mapeado, o Agente deve responder: "Qual fase/componente downstream poderia absorver ou mascarar o problema que estou avaliando aqui?"
8. **Lei do Isolamento por Turnos (Anti-Autoregressive Bias):** Para quebrar o viés de geração contínua, o Agente é ESTRITAMENTE PROIBIDO de criar e testar no mesmo turno. O ciclo é assíncrono: No **Turno 1**, o Agente redige a Dissertação, salva a evidência e encerra a resposta acionando a ferramenta `schedule` (Timer de 1s) para forçar a Auditoria do Turno 2. No **Turno 2**, o sistema o acordará como Inquisidor para o Teste Real. Concluído o Teste com sucesso, o Agente volta a engatilhar o `schedule` para o Turno 1 da etapa seguinte. Você NUNCA delega ao usuário o trabalho mecânico de pedir para continuar.

9. **Lei do I/O Seguro (Anti-Deadlock):** O Agente é ESTRITAMENTE PROIBIDO de usar scripts Python externos para manipular artefatos de IDE (`task.md`, `implementation_plan.md`, `walkthrough.md`). Para escrita de artefatos, SEMPRE usar as Tools Nativas (`write_to_file`, `replace_file_content`). Scripts externos só podem tocar arquivos de dados e config (JSON, logs, estado de runtime). A violação desta lei é a causa raiz de congelamentos do terminal no WSL/Linux.

10. **Lei do Hook Resiliente (Anti-SPOF):** Qualquer script de Lifecycle Hook (`pre_invocation`, `circuit_breaker`, `stop_hook`) DEVE distinguir entre dois eventos fundamentalmente diferentes: (a) **Violação real na payload** → BLOQUEAR (`sys.exit(1)`) e registrar; (b) **Erro interno do próprio hook** → LIBERAR (`sys.exit(0)`) e registrar como degradação. O Hook nunca pode ser o Ponto Único de Falha que paralisa o Agente inteiro. Um hook defeituoso deve sinalizar sua disfunção, não travar o sistema.

11. **Lei dos 3 Modos de Hook:** Todo hook de segurança do projeto DEVE operar em 3 modos explícitos: `GUARDIAN` (padrão — julga todas as intenções), `DEGRADED` (ativado automaticamente após N erros internos consecutivos — libera com alerta obrigatório), `BYPASS` (ativado manualmente com timestamp de expiração obrigatório — máximo 120 minutos). A transição `GUARDIAN→DEGRADED` é automática. A saída do modo `DEGRADED` exige intervenção humana via CLI admin. O modo `BYPASS` deve ser revogável a qualquer momento.

12. **Lei do Estado Atômico (Anti-Corrupção de Arquivo):** Qualquer escrita de arquivo de estado crítico (ex: `cb_state.json`, `sonar_report.json`) DEVE seguir o padrão POSIX de rename atômico: `tempfile.mkstemp()` no mesmo diretório → escrever no temp → `os.replace(tmp, destino)`. Nunca abrir o arquivo final diretamente para escrita (risco de corrupção em falha de processo). Se o estado estiver corrompido ou ausente na leitura, o sistema DEVE assumir o modo padrão seguro (ex: GUARDIAN) e nunca travar.

13. **Lei da Revisão Honesta do Council:** Ao invocar o Singularity Council, o Agente DEVE ler os arquivos físicos reais (`view_file`) antes de emitir qualquer julgamento. Críticas devem ser baseadas exclusivamente no código que existe no disco, dentro das limitações documentadas nos micro-passos (`docs/micro_etapas/`). É expressamente proibido: (a) inventar problemas que não existem no código real; (b) mascarar ou suavizar problemas reais por auto-complacência; (c) usar pseudocódigo ou memória de conversa como substituto para a leitura física dos arquivos.

14. **Lei da Execução Desacoplada no Shell (Anti-Hanging):** Para prevenir travamentos silenciosos (Working infinito), o Agente é ESTRITAMENTE PROIBIDO de utilizar operadores de encadeamento longos (`&&`) ou wildcards perigosos (`*`) em operações de cópia/I/O no host.
    - Toda operação de FileSystem via Shell deve ser atômica e observável (ex: rodar `mkdir` separado de `cp`).
    - Para copiar o conteúdo integral de um diretório, sempre utilize o padrão POSIX seguro `cp -r source/. dest/` no lugar de `source/*` para garantir a inclusão de arquivos ocultos e evitar erros de expansão.
    - Operações de cópia e I/O crítico em terminal DEVEM terminar com um marcador explícito (ex: `echo "COPY_COMPLETE"`) para provar o retorno do controle ao Agente.
    - Se um terminal travar, o Agente é proibido de usar `rm` ou `kill` agressivamente sem antes executar testes simples (`echo START && pwd`) para diagnosticar se o problema é o wrapper da IDE ou um pipe aberto.

15. **Lei do Anti-Loop Estático (Evolução Cognitiva Obrigatória em Execuções Longas — Falha Empiricamente Documentada em 2026-08-19):** Em qualquer geração de artefatos em série (N > 10 arquivos em sequência), o Agente é ESTRITAMENTE PROIBIDO de usar rotação mecânica de um catálogo fixo de exemplos, problemas ou domínios (ex: `(step - 1) % N`). Cada 25% do volume total DEVE introduzir pelo menos um problema, domínio, técnica arquitetural ou dimensão de análise que **não apareceu** nos 25% anteriores. A entropia cognitiva de uma sequência longa deve crescer, nunca convergir para um loop fechado. Um sistema que repete o mesmo padrão a cada N ciclos não demonstra raciocínio — demonstra paginação de template.

16. **Lei da Delegação Única de Eventos e Integridade de Cascata (Anti-Double-Listener & CSS Scope):**
    - **Fonte Única de Eventos:** Ao utilizar delegação genérica de eventos (ex: `querySelectorAll('[data-action]')`), o Agente é ESTRITAMENTE PROIBIDO de anexar `addEventListener` individuais aos mesmos elementos abaixo no script. A duplicação de ouvintes gera cancelamento imediato de toggles booleanos (0ms race condition) invisível a linters estáticos.
    - **Hierarquia de Seletores Globais de Tema:** Atributos de tema (ex: `data-theme="light"`) DEVEM ser aplicados prioritariamente no elemento raiz (`document.documentElement`) e espelhados no `document.body`. No CSS, as regras devem utilizar `:root[data-theme="light"], html[data-theme="light"], body[data-theme="light"]` e `html[data-theme="light"] body::before`, nunca seletores descendentes órfãos (`[data-theme="light"] body::before`) que quebram o escopo.
